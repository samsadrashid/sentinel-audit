**Status:** Architecture decisions complete (updated 2026-11-08). Q1–Q8 are answered, O-01–O-10 are resolved (D-15–D-24), the architecture review corrections are recorded (D-25–D-32), the pre-freeze blockers are resolved (D-33–D-35), the approval nonce and expiry model is decided (D-36, D-37), and operator signing is algorithm-agile (D-38). On 2026-11-09 the signing architecture was decided: a dedicated signing device with per-key roles (D-45), signed registry checkpoints (D-46), and Secure Enclave operator keys plus ES256 FIDO2 recovery (D-47, amending D-38), with operational resolutions OD-2 to OD-6 (§4.1). D-39 was withdrawn and D-40 to D-44 were recorded on 2026-11-09. **The architecture is frozen as a design baseline (D-48, 2026-11-09).** This is not M1 completion and not production-signing approval. See the decision log (§4). **Scanner implementation is blocked** until both the architecture and the specifications are approved.

Sentinel is a security assessment platform for software and infrastructure that the operator owns or is authorised to assess. It works in three execution modes: READ, VALIDATE and RED TEAM. Read-only assessment is the default. Every active step requires authorisation that is recorded and checked against a defined scope. The architecture document, `docs/architecture/discovery.md`, has not been written yet.

## 2. Discovery process

1. **Problem brief.** One page covering goals, non-goals, users and the threat model if it's a security scanner. Output: `docs/product/brief.md`.
2. **Reference analysis.** Two to four comparable tools: what to adopt, adapt or reject. Output: `docs/reference-analysis/`.
3. **Architecture options.** Two or three candidate architectures, for example a plugin-based rule engine vs a pipeline of independent analyzers vs a service with workers. Each with trade-offs and a recommendation. Output: `docs/architecture/options.md`.
4. **Red-team review** of the chosen option: failure modes, scale, security of the scanner itself (untrusted input parsing, sandboxing, secrets in findings). Output: `docs/architecture/review.md`.
5. **Architecture decision records** for each major choice. Output: `docs/adr/NNNN-*.md`.
6. **Specifications.** Scanner interface contract, finding schema, rule/plugin API, config format, CLI/API surface, report formats. Testable requirements with IDs. Output: `docs/specs/`.
7. **Test strategy and milestone plan**, test-first. Output: `docs/plan/milestone-1.md`.
8. **Approval gate.** You approve the architecture and specs. Only then does scanner implementation start.

## 3. Ground rules

- Every change is planned before any code. Commits, pushes, deploys, migrations and global settings changes each need explicit approval under Sentinel's own approval policy (D-20).
- Code and findings must not go to external LLMs or services without approval.
- If Sentinel scans third-party targets, authorisation and scope rules are part of the spec, not an afterthought.
